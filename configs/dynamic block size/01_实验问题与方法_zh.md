# 动态 block size：实验问题与方法

## 1. 研究问题

目标 serving 形态是：同时维护大量 request，为每个 request 预测下一轮合适的 block size，再把相同 block size 的 request 分桶组成 batch。候选为 `L ∈ {8,16,32}`，初始轮使用 L16。

需要回答三个问题：

1. 缩短 lookahead 是否会破坏原本位于小 block 范围内的接收潜力？
2. 只使用当前轮之前的历史，能否判断下一轮接收能力，从而选择 L8/L16/L32？
3. 当历史本身由动态 block 产生、存在“整块通过但不知道真实上限”的删失时，信号是否仍可靠？

设计原则是保守使用大 block。以 L8→L16 为例，如果额外计算 8 个位置只多接收 1 个 token，即使算法 TPF略有增加，在大 batch compute-bound 场景也未必划算。因此目标标签同时考虑绝对接收增益和单位新增 block 位置的收益。

## 2. 第一阶段：PyTorch 同状态多 block shadow

### 2.1 目的

第一阶段不训练动态策略。它以正常 L16 LinearSpec 为 canonical，在每一轮相同 causal prefix、KV、seed token 上真实运行 L4/L8/L16/L32 draft-verify，记录 `A4、A8、A16、A32`。

该实验回答“block size 本身是否改变靠前接收”以及“大 block 的接收优势来自哪里”。只有 L16 分支真正提交；其他分支只用于观察。

### 2.2 容量尾部与区间内衰减

对小 block `L1` 和大 block `L2`，定义：

- 总增益：`Delta = A_L2 - A_L1`；
- 容量尾部：`Tail = max(A_L2 - L1, 0)`；
- 区间内衰减：`Decay = Delta - Tail`。

例 1：`A8=5，A32=7`。

- 总增益为 2；
- A32 没有超过 L8 容量，Tail=0；
- Decay=2，说明缩短 lookahead 后，即使在前 8 个位置内也少接收了 2 个。

例 2：`A8=8，A32=20`。

- 总增益为 12；
- 超过 L8 容量的尾部正好是 12；
- Decay=0，说明 L8 范围内没有额外损失，大 block 优势完全来自能继续接收第 9～20 个 token。

还定义条件生存率：

`S(L1,L2,k) = P(A_L1 ≥ k | A_L2 ≥ k)`。

它回答：已知大 block 能接收到第 k 个 token 时，小 block 还能接收到第 k 个的概率。例如 `S(8,32,8)=0.94` 表示当 L32 至少接收 8 个时，L8 也至少接收 8 个的概率约为 94%。

### 2.3 数据排除

主分析排除任一分支命中 EOS、剩余生成预算不足 32 等无法公平比较的轮次。AIME24 可保留原始结果，但不进入宏平均。

## 3. 第二阶段：SGLang 动态 canonical + 三分支 shadow

### 3.1 为什么必须重新采集动态历史

第一阶段历史始终来自 L16。真实动态策略运行后，上一轮可能是 L8、L16 或 L32；如果直接用固定 L16 历史训练，可能产生明显分布偏移。

第二阶段在修复后的 SGLang+NeMoSkills LinearSpec 上运行。每个 request 每轮先只看过去历史选择动作 `L_t`，随后在当前同一状态下真实运行 L8/L16/L32 三个分支，只有预先选中的 canonical 分支提交。下一轮历史也只追加 canonical 结果。

核心时序如下：

```text
历史 H_t
  -> 在看不到当前轮 shadow 的情况下选择 L_t
  -> 同状态运行 L8/L16/L32
  -> 只提交预先选择的 L_t
  -> 将该 canonical 结果加入 H_(t+1)
```

物理 KV 槽按 L32 预留。为避免不同长度 ForwardBatch 复用共享元数据产生异步错误，每个 shadow 分支结束后执行 CUDA correctness barrier；canonical 分支最后执行并直接提交。该设计优先保证标签正确，不评价 shadow 实验本身的速度。

### 3.2 探索策略

每个 request 第一轮固定 L16。探索阶段根据上一轮 block 使用分层 Markov 行为策略：

|上一轮|下一轮 L8|下一轮 L16|下一轮 L32|
|:---:|:---:|:---:|:---:|
|L8|55%|35%|10%|
|L16|25%|50%|25%|
|L32|10%|35%|55%|

探索动作只负责覆盖不同动态历史；训练标签来自每轮同时得到的同状态 `A8/A16/A32`。

### 3.3 数据集、切分与权重

使用九个非 AIME24 数据集：

`GSM8K、HumanEval、MBPP、MATH-500、AIME25、GPQA、IFEval、LiveCodeBench-C++、MMLU`。

MMLU 默认最多取 2000 个样本。每个 prompt 根据稳定 SHA-256 指纹划分：

- 70% request：训练；
- 15% request：selection，搜索标签规格、模型族和动作阈值；
- 15% request：严格 held-out test。

所有全局拟合和指标始终采用：

`数据集等权 -> 数据集内 request 等权 -> request 内有效轮次等权`。

数据集 ID 不进入特征，不允许为每个数据集设计一套策略。条件指标“大精/大浪/8安”也先在每个存在该动作的数据集内部计算，再对数据集等权平均。

## 4. 动态历史特征

当前轮只能使用以前真正提交的 canonical 历史。

### 4.1 接收特征

- 上一轮 block size、接收长度、接收比例、是否整块通过；
- 最近 1/2/4/8 轮平均接收长度；
- 最近 1/2/4/8 轮平均接收比例；
- 最近 2/4/8 轮整块通过率；
- 最近 4 轮接收长度和接收比例趋势；
- 连续整块通过轮数 `full_streak`；
- 连续非整块通过轮数 `nonfull_streak`。

### 4.2 删失感知特征

动态 block 的关键问题是：L8 整块通过只说明能力至少为 8，不能据此判断能力是否超过 8。

对阈值 8 和 16，分别统计最近 1/2/4/8 轮：

- `gt8/gt16_known_rate`：在结论可知的历史轮中，能力确实超过阈值的比例；
- `gt8/gt16_known_n`：有多少轮能够判断该结论。

一轮只有满足下列任一情况时，才对“是否超过阈值”提供已知标签：

- 实际接收长度已经超过阈值：已知为真；
- 当轮 block 大于阈值且没有超过：已知为假；
- 当前 block 未满且接收提前停止：已知为假。

例：上一轮选择 L8 且整块通过，`A≥8`，但“是否大于 8”未知；选择 L16 只接收 6，则已知“不大于 8”和“不大于 16”。

### 4.3 confidence 特征

每轮 canonical 记录 draft 开头最多 7 个位置的平均 confidence、margin、entropy，以及首个拒绝位置的 confidence/margin。保存上一轮值和最近 1/2/4/8 轮移动平均。

最终 S8 模型选择了包含这些特征的 `confidence` 组；最终 S16 模型只选择了接收+删失的 `censor` 组。

## 5. 四个概率指标

四个概率都是逻辑回归根据历史 `H_t` 输出的带权训练分布分数，不是当前轮 shadow 结果，也不应未经校准直接解释为真实频率。

### 5.1 默认 L8 目标

`P(worth16)` 预测 L16 相比 L8 是否值得：

- `A16 - A8 ≥ 2`；
- `(A16 - A8) / 8 ≥ 0.125`。

最终规格中第一项更严格，实际等价于至少多接收 2 个 token。

`P(worth32)` 预测 L32 相比 L8 是否值得：

- `A32 - A8 ≥ 5`；
- `(A32 - A8) / 24 ≥ 0.125`。

最终实际等价于至少多接收 5 个 token。它是 L32 对 L8 的直接比较，不是 L32 对 L16 的增量比较。

冻结动作规则：

```text
第一轮：L16
否则若 P(worth32) >= 0.6：L32
否则若 P(worth16) >= 0.6：L16
否则：L8
```

两个概率由独立二分类器给出，没有强制单调一致；若二者同时超过阈值，L32 优先。

例：

|P32|P16|动作|解释|
|:---:|:---:|:---:|:---|
|0.72|0.85|L32|两者都通过，L32 优先。|
|0.54|0.73|L16|没有足够证据选 L32，但支持 L16。|
|0.41|0.57|L8|没有明确的大块收益信号。|

### 5.2 默认 L16 目标

`P(worth32)` 预测 L32 相比 L16 是否值得：

- `A32 - A16 ≥ 5`；
- `(A32 - A16) / 16 ≥ 0.125`。

最终实际等价于至少多接收 5 个 token。

`P(safe8)` 预测降到 L8 是否不会损失 L16 的接收能力：

`A16 - A8 ≤ 0`，即 `A8 ≥ A16`。

这不代表 L8 接收很多。`A8=A16=3` 也属于 safe8；它只表示 L8 相对 L16 没有损失。

冻结动作规则：

```text
第一轮：L16
否则若 P(worth32) >= 0.6：L32
否则若 P(safe8) >= 0.98：L8
否则：L16
```

若两个条件同时满足，升级 L32 优先。当前真实运行中 safe8 几乎不触发。

## 6. 训练和策略搜索

候选模型包括带 L2 正则的逻辑回归和深度 3 浅树；深度 3/6 的 GBDT 只用于估计信号上界，不导出 serving 策略。缺失历史特征使用训练集均值填补，逻辑回归特征按训练均值和标准差标准化。

搜索空间为：

- S8：`gain16 ∈ {2,3,4}`，`eff16 ∈ {0.125,0.25}`，`gain32 ∈ {5,7,9}`，`eff32 ∈ {0.125,0.25}`；
- S16：`gain32 ∈ {3,5,7}`，`eff32 ∈ {0.125,0.25}`，`safe8_loss ∈ {0,1}`；
- 特征组：accept、censor、confidence；
- 动作概率阈值：`0.50、0.60、0.70、0.80、0.85、0.90、0.95、0.98`。

selection 上优先要求：

- 大块显著收益率至少 80%；
- 大块浪费率至多 10%；
- S16→L8 安全率至少 98%。

可行候选按 `接均 - 0.10 × 块均` 排序；若没有可行候选，代码会在违反约束的候选中按惩罚后效用选一个结果。因此必须同时检查“是否满足约束”，不能只看到生成了策略文件就认为策略合格。当前 S8 就属于没有可行候选后的回退结果。

## 7. serving 落地形态

观察阶段同一 request 同时运行三个 block 只为获取标签。部署阶段应只执行策略选中的一个 block，并按动作分桶：

```text
等待队列中的 request
  -> 分别计算下一轮动作 8/16/32
  -> L8 桶组成 L8 batch
  -> L16 桶组成 L16 batch
  -> L32 桶组成 L32 batch
```

这样每个 batch 内 block 一致，不必统一 padding 到最大 L32。SGLang 更适合实现连续 batching、KV 管理和分桶调度；PyTorch 可以验证算法，但需要自行实现 serving scheduler 才能公平测量生产形态。

必须最终测量：真实处理 token 数、真实 TPF、吞吐、TPOT、请求延迟、桶等待时间、桶内 batch 利用率和 GPU 利用率。仅有离线 `接均/块均` 不能替代这一步。
